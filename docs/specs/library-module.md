## 1. Executive Summary & Purpose

The **Library Module** manages the physical voucher code economy of AlphaZero, enabling students in low-connectivity, cash-dominant regions (such as Syria and the broader MENA region) to purchase physical access cards at local brick-and-mortar retail libraries and redeem them for digital course access.

This document serves as the **single authoritative specification** for the Library module. It consolidates:
1. An exhaustive **18-story matrix** linking user personas, lifecycle touchpoints, API endpoints, permissions, fraud detection signals, and automated test coverage.
2. A formal **GLOSSARY** defining all load-bearing domain terminology.
3. The four **ratified spec amendments** with complete architectural rationale.
4. A **Gaps Analysis** detailing discrepancies between the original Product Requirement Document (PRD), API inventory, and implemented production endpoints.

## 2. Domain Glossary

The following vocabulary is load-bearing across all domain aggregates, command handlers, presentation endpoints, and audit ledgers:

| Term | Formal Definition | Lifecycle & System Impact |
| :--- | :--- | :--- |
| **Mint** | The cryptographic generation and database persistence of one or more access codes in `Minted` status. The plaintext code string is derived via cryptographically secure pseudo-random generation, hashed (PBKDF2/HMAC-SHA256), and stored as `CodeHash`. The plaintext code is returned **once** to the issuer and never persisted in plaintext. | Initial lifecycle entry point for access codes. Codes are bound to a `TenantId`, an optional `LibraryId`, a `TargetResourceArn`, an execution `StrategyId` (default `enroll-course`), a monetary `FaceValue`, and metadata. |
| **Sell** | The retail point-of-sale (POS) commercial event where a physical voucher card is transferred to a customer and financial consideration (cash) is collected at the counter. | Generates an auditable sale event. Per ratified amendment, `Sold` is a recorded audit event rather than a blocking prerequisite for student redemption. |
| **Distribute** | The bulk administrative state transition transitioning a batch of access codes from `Minted` to `Distributed` status (`AccessCodeStatus.Distributed`). | Signifies physical consignment and handover of printed cards to a specific library branch. Only `Minted` codes can be distributed; once distributed, codes become sellable at that retail location. |
| **Redeem** | The operation performed by an authenticated student submitting a valid plaintext code via `POST /library/redeem` to unlock course access. | Transitions code from `Distributed` or `Minted` to `Redeemed` status. Sets `RedeemedAt` and `RedeemedByUserId`, records an immutable `RedemptionAuditLog` (with client IP and device fingerprint), and executes the associated `IRedemptionStrategy`. Re-redeem by the same user succeeds idempotently. |
| **Void** | The terminal administrative invalidation of an access code from any status (`Minted`, `Distributed`, or `Redeemed`), requiring an explicit, non-empty audit `Reason`. | Sets `Status = AccessCodeStatus.Voided` and writes `VoidedReason`. If the code was previously redeemed, dispatches `AccessCodeVoidedDomainEvent` to trigger asynchronous revocation of the student's course enrollment. A voided code cannot be re-voided or redeemed. |
| **Expire** | The state transition where an unredeemed code exceeds its contractual validity period or operational shelf-life. | Renders the code permanently unredeemable. Prevents stale cards from being redeemed after curriculum obsolescence or contract termination. |
| **SaleRecord** | An immutable audit record capturing the point-of-sale transaction details (timestamp, library ID, batch ID, face value, currency, worker ID) when a card is sold. | Serves as the commercial source of truth for revenue attribution, wholesale settlement, and discrepancy matching against downstream redemptions. |
| **AdminCode** | A standalone access code minted directly at the tenant level with an `ADM-` prefix, not associated with any physical library branch (`LibraryId = null`). | Minted via `POST /library/admin/access-codes/generate-single` by Tenant Administrators for corporate sponsorships, VIP grants, or operational administrative overrides. |
| **Batch** | A logical collection of access codes minted simultaneously for a single library under a unified `BatchId`, sharing target resource ARN, face value, metadata, and creation timestamp. | Unit of bulk physical printing, consignment tracking, distribution, and wholesale reconciliation. |
| **Outstanding** | An aggregate inventory calculation representing all active codes currently in circulation that have not reached a terminal state: $\text{Outstanding} = \text{Minted} + \text{Distributed} - (\text{Redeemed} + \text{Voided} + \text{Expired})$. | Key metric used by accountants and managers to evaluate retail float, physical stock levels, and commercial exposure. |

## 3. Ratified Spec Amendments & Rationale

During design review and production hardening (Tier-0), four critical architectural amendments were ratified. These deviations from initial naive models are deliberate, load-bearing system behaviors:

### Amendment A: Idempotent Re-Redemption
- **Specification:** If an authenticated student attempts to redeem an access code that is already in `Redeemed` status, the endpoint inspects `RedeemedByUserId`. If `accessCode.RedeemedByUserId == currentUser.UserId`, the command handler short-circuits and immediately returns `200 OK` (`Result.Success`). If the code was redeemed by a different user, it returns `409 Conflict` (`AccessCode.InvalidStatus`).
- **Rationale:** Students in Syria and MENA frequently operate on intermittent, high-latency 2G/3G mobile networks. A common failure mode is an HTTP response packet dropping after the database transaction has committed. Without natural idempotency, the client app's automatic retry would receive a `409 Conflict`, causing panic, user complaints, and unnecessary support escalation under the false impression that their purchased card was burned or stolen.

### Amendment B: Sold as Recorded Event, Not a Redeem Gate
- **Specification:** `Sold` is an asynchronously recorded point-of-sale event, **NOT** a hard blocking prerequisite for `POST /library/redeem`. Codes in `Distributed` (and even unbatched `Minted` admin codes) are eligible for redemption immediately upon entering the raw string. If an access code is redeemed without a prior `SaleRecord`, the redemption succeeds for the student, but the system logs a high-priority fraud signal into the Accountant's reconciliation queue.
- **Rationale:** Retail library counters in target markets frequently experience power outages, hardware failures, or internet blackouts while remaining open for cash business. Requiring a synchronous online POS check before a student can scratch and redeem their card at home would violate the core offline-first product premise. Students are protected from retail connectivity failures; financial accountability is resolved asynchronously between AlphaZero and the library.

### Amendment C: Refunds Record-Only via Void-with-Reason
- **Specification:** Customer refunds or returned physical cards are handled via `POST /library/access-codes/void` with a mandatory descriptive `Reason` parameter (enforced at both validation and domain aggregate layers). The software platform does not implement complex multi-currency cash payout engines or automated banking reversals in MVP.
- **Rationale:** The physical code economy operates entirely on wholesale cash settlement in physical currency (e.g., SYP). Real-world customer refunds occur across the physical retail counter in cash. The platform's sole responsibility is cryptographic invalidation, audit logging, and downstream enrollment revocation (via `AccessCodeVoidedDomainEvent`) to prevent double-spending and ledger fraud.

### Amendment D: AttachCourses Owned by the Accountant
- **Specification:** The permission `library:AttachCourses` and its corresponding endpoints (`POST /library/libraries/{Id}/resources` and `DELETE /library/libraries/{Id}/resources`) belong exclusively to the **Library Accountant** (AlphaZero / Tenant administrative authority), **NOT** the **Library Manager**.
- **Rationale:** A Library Manager represents the retail distribution franchisee. Allowing retail managers to authorize which courses their own shop is licensed to sell creates a severe conflict of interest (risk of self-granting unauthorized high-value courses). AlphaZero or the Tenant institution acts as the content rights-holder; therefore, course catalog mapping must be strictly controlled by the central Accountant role.

## 6. Gaps Analysis

This section identifies all known defects, unimplemented PRD specifications, and structural discrepancies between documentation, user stories, and code:

### 6.1 PRD Specifications Without Matching Production Endpoints
1. **Library Worker Code Generation Discrepancy:**
   - *PRD Line:* Section 4 table states: *"Library Worker: Retail point-of-sale; retrieves/generates codes for customers."*
   - *Production Reality:* In production and test enforcement (`PermissionWiringTests.GenerateAdminCode_Worker_Should_Return403Forbidden`), Library Workers have **zero** code generation permissions. Permitting retail counter clerks to generate cryptographic access codes on demand represents an unacceptable counterfeiting vulnerability. Code generation is strictly restricted to Library Managers and Tenant Administrators.
2. **Dedicated Point-of-Sale Sale Recording Endpoint:**
   - *PRD Line & Story 8:* *"As a Library Worker, I want to record the sale of a code at the point of sale..."*
   - *Gap:* The API currently has no `POST /library/access-codes/sale` endpoint. Codes transition directly from `Minted` $\rightarrow$ `Distributed` $\rightarrow$ `Redeemed`. Sales are audited retroactively through redemption logs rather than counter-side POS invocations.
3. **Single-Action Batch Recall Endpoint:**
   - *Story 6:* *"As a Library Manager, I want to recall an entire batch with one action..."*
   - *Gap:* There is currently no `POST /library/access-codes/batches/{BatchId}/void` endpoint. Batch invalidation must currently be performed by sequentially invoking `POST /library/access-codes/void` per code.
4. **Tenant-Wide Un-Scoped Audit Log Endpoint for Accountant:**
   - *Story 10:* *"As a Library Accountant, I want tenant-wide audit logs..."*
   - *Gap:* Following Tier-0 fix `#48`, `GetRedemptionLogsEndpoint` requires a non-empty `LibraryId` and scopes authorization strictly to `ResourceArn.ForLibrary(...)`. The legacy tenant-wide fallback path was removed to prevent Library Managers from reading other libraries' data. A dedicated `GET /library/audit-logs` endpoint with `ResourceArn.ForTenant` authorization is missing for the Accountant.
5. **Specialized Fraud Queue and Failed Provisioning Queue Endpoints:**
   - *Stories 14 & 15:* Specifying a fraud-flag queue (unsold redemptions, void-after-redeem, velocity anomalies) and failed-provisioning queue.
   - *Gap:* While events and exceptions are logged into `RedemptionAuditLog` and system logs, specialized query endpoints (e.g., `GET /library/fraud/queue`, `GET /library/provisioning/failures`) have not yet been materialized.
6. **Aggregated Inventory Funnel & Revenue Endpoints:**
   - *Stories 12 & 13:* Specifying stock funnels (Minted/Distributed/Sold/Redeemed/Voided/Expired/Outstanding) and periodic revenue attribution per library.
   - *Gap:* No dedicated aggregation endpoints (e.g., `GET /library/libraries/{Id}/funnel` or `GET /library/libraries/{Id}/revenue`) exist; consumers must calculate funnels manually from raw logs.
7. **Automated Background Code Expiration:**
   - *Glossary & Story 12:* Defining the `Expired` state.
   - *Gap:* The domain `AccessCodeStatus` enum contains `Minted`, `Distributed`, `Redeemed`, and `Voided`. `Expired` is not yet an enum value, and no background worker exists to sweep expired codes.
